Based on your confirmed architecture, the single object that owns all 32 children is the `infrastructure` Kustomization in `flux-system`. So the command was almost certainly one of these (all three do the same thing):

```bash
kubectl delete kustomization infrastructure -n flux-system
# or the flux CLI equivalent (defaults to the flux-system namespace):
flux delete kustomization infrastructure
# or if he deleted it from a manifest file:
kubectl delete -f <some-path>/infrastructure.yaml
```

Any of those → `infrastructure`'s finalizer fires → prunes all 32 children → every addon gone → and since `infrastructure` is an unowned apex, nothing brings it back.

> Note the exact name: the children carry prefixes (`apps.fbg.…`, `apps.fmx-msk.…`), but the apex was just plain `infrastructure`. So the lethal command is literally `delete kustomization infrastructure`. The scary part is how *innocuous* it looks — it reads like deleting "one thing."

## How to confirm *which* command he actually ran

The cluster recorded it — two places to look:

```bash
# 1. Flux's own controller log — it logs the prune cascade it performed:
kubectl logs -n flux-system deploy/kustomize-controller | grep -iE 'infrastructure|prune|delet|garbage'

# 2. Kubernetes audit log (if enabled on the API server / EKS CloudTrail) —
#    this names the USER, the verb, and the timestamp:
#    look for: verb=delete  resource=kustomizations  name=infrastructure
```

On EKS specifically, that delete shows up in **CloudTrail** as an EKS audit event — `verb: delete`, `objectRef.resource: kustomizations`, `objectRef.name: infrastructure`, plus the IAM identity and exact time. That's your forensic proof of who ran it and when.
