## Part 1 — How we deployed the home lab (summary)

**`lab-hardway` — a bare-metal, 3-node GitOps platform, built as a portable bank-grade base template.**

**Two-repo split**
- `platform-k8s-infrastructure` — everything below the workload tier (storage, certs, policy, ingress, observability, Kafka, Flux itself).
- `platform-k8s-apps` — the workloads (Online Boutique tenant).

**Bootstrap (one command + one out-of-band secret)**
1. Seed the `sops-age` Secret by hand (Flux needs it to decrypt the very first reconcile — chicken-and-egg).
2. `flux bootstrap github --path=clusters/lab-hardway --token-auth` (classic PAT). This installs the 4 controllers, commits their manifests back, and plants the `flux-system` GitRepository + root Kustomization.

**The wiring — Pattern X (the key bit vs the office)**
- The **root `flux-system` Kustomization** renders `clusters/lab-hardway/`, whose `kustomization.yaml` lists exactly **three** things: `flux-system/`, `infrastructure.yaml`, `apps.yaml`.
- `infrastructure.yaml` is a **file** (not an object) declaring **16 Flux Kustomizations**, one per component.
- Because the root renders that file, **the root directly owns all 16** — they all self-heal, and there is **no intermediate `infrastructure` apex object** to delete.
- `components/` holds only cluster-agnostic workload CRs; cluster-specifics live in `clusters/<name>/` + a `cluster-vars` ConfigMap injected via `postBuild.substituteFrom`. → portable to any cluster by copying one folder.

**The dependency cascade (Tier model, ordered by `dependsOn`)**
- Tier 0: `local-path-provisioner` (storage)
- Tier 1: controllers/operators — `cert-manager`, `kyverno`, `metallb`, `envoy-gateway`, `reloader`, `datadog-operator`, `strimzi-cluster-operator` + `config` + `secrets`
- Tier 1 CR-pairs (CRD-then-CR): `cert-manager-issuers`, `kyverno-policies`, `metallb-config`
- Tier 2 operator-CRs: `datadog-agent`, `kafka-clusters`, `platform-gateway` (these use `wait: false` + explicit `healthChecks`, because the operator spawns the real pods out-of-band)
- Tier 3: `apps` → boutique

**Ingress path:** MetalLB (L2, pool `192.168.8.16-31`) → Envoy Gateway (Gateway API, replacing EOL ingress-nginx) → `platform-gateway` (TLS from cert-manager internal CA) → boutique `HTTPRoute`.

**The two acceptance goals (both proven this session):**
1. **One-click install AND delete** — `flux-bootstrap.sh` cold-boots to all-Ready in ~3 min; `flux-cleanup.sh` tears down to a pristine "Layer 0" and asserts it.
2. **Portability** — `components/` stay cluster-agnostic; a new cluster = copy `clusters/<name>/` + edit `cluster-vars`.

**Resilience property (the contrast with the office incident):** every component is owned by the self-managing root, so deleting any one leaf self-heals. The only irreducible apex is the bootstrap root itself.

You are looking at our office Flux cluster (context: the fanatics-exchange / dev-1

I've been studying a separate home-lab GitOps platform ("lab-hardway") and I want
you to compare our office setup against it, focused on RESILIENCE and BLAST RADIUS.
Here is how the home lab is wired:

— Two repos: platform-infra + apps.
— Bootstrap: `flux bootstrap … --path=clusters/lab-hardway`. The ROOT `flux-system`
  Kustomization renders clusters/lab-hardway/, whose kustomization.yaml lists exactly
  three things: flux-system/, infrastructure.yaml, apps.yaml.
— infrastructure.yaml is a FILE declaring 16 separate Flux Kustomizations (one per
  component: cert-manager, kyverno, metallb, envoy-gateway, reloader, datadog-operator,
  strimzi, plus CRD-then-CR pairs and operator-CRs).
— CRITICAL: because the root renders that file, the root DIRECTLY OWNS all 16
  component Kustomizations. There is NO intermediate "infrastructure" Kustomization
  object. Running `kubectl get kustomizations -o custom-columns=NAME,OWNED-BY:
  .metadata.labels.kustomize\.toolkit\.fluxcd\.io/name` shows EVERY component
  OWNED-BY: flux-system. The only unowned apex is the bootstrap root itself.
— Consequence: deleting any single component Kustomization self-heals (the root
  recreates it). There is no single object whose deletion takes down all addons
  without recovery.
— Components are cluster-agnostic; cluster specifics come from a cluster-vars ConfigMap
  via postBuild.substituteFrom. dependsOn encodes boot order. Operator-CR Kustomizations
  use wait:false + healthChecks. prune:true throughout. One-click teardown script
  asserts a pristine baseline.

CONTEXT — why I care: someone once deleted our office `infrastructure` Kustomization
and ALL addons disappeared and did NOT come back. We established that our office
`infrastructure` Kustomization owns ~32 child Kustomizations and is itself an UNOWNED

path), so nothing recreated it.

   unowned apexes (null owner label). Confirm whether `infrastructure` is owned by

2. Blast radius: how many children does `infrastructure` own? What is the single
   most dangerous `kubectl delete` on this cluster?
3. Self-heal gap: for each unowned apex, state explicitly what would NOT recover
   automatically if deleted, and what the recovery procedure is (re-apply vs
   re-bootstrap).
4. Path analysis: print the root's spec.path and infrastructure's spec.path. Explain
   whether infrastructure's manifest lives inside the root's rendered tree (and is
   therefore fixable to be self-healing) or not.
5. Recommendation: give the concrete, minimal change that would make our office
   `infrastructure` self-healing like the home lab — i.e. declare it inside the root's
   path so the root owns and recreates it — WITHOUT having to flatten everything into
   16 separate root-owned Kustomizations. Note the trade-offs.
6. Also flag any OTHER unowned apexes besides `infrastructure` (e.g. the apps
   aggregator) that carry the same delete-and-it-never-comes-back risk.

Output a side-by-side table (office vs home-lab) plus a prioritized remediation list.
Do not change anything — diagnosis and recommendations only.
