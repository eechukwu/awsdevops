Here's a tighter read-only set built specifically to make the **apex-vs-owned** distinction visible. The trick: Flux stamps every object it manages with a label naming its owner — so you can literally ask each Kustomization "who created you?"

```bash
# ─────────────────────────────────────────────────────────────
# A. THE OWNERSHIP TABLE — each Kustomization and WHO OWNS IT
#    (the label kustomize.toolkit.fluxcd.io/name = the parent that applied it)
# ─────────────────────────────────────────────────────────────
kubectl get kustomizations -n flux-system \
  -o custom-columns='NAME:.metadata.name,OWNED-BY:.metadata.labels.kustomize\.toolkit\.fluxcd\.io/name'
```
**What you'll see:** the 32 children show `OWNED-BY: infrastructure`. But `infrastructure` itself and the root `flux-system` show **`<none>`** — that blank is the signature of an **apex object** (nobody applied it via Flux → nobody will recreate it).

```bash
# ─────────────────────────────────────────────────────────────
# B. LIST EVERY APEX OBJECT — the Kustomizations with NO owner
#    (these are the ONLY ones that won't self-heal if deleted)
# ─────────────────────────────────────────────────────────────
kubectl get kustomizations -n flux-system -o json \
  | jq -r '.items[] | select(.metadata.labels["kustomize.toolkit.fluxcd.io/name"] == null) | .metadata.name'
# no jq? use this instead:
kubectl get kustomizations -n flux-system \
  -o custom-columns='NAME:.metadata.name,OWNER:.metadata.labels.kustomize\.toolkit\.fluxcd\.io/name' \
  | grep '<none>'
```
**What you'll see:** `flux-system` and `infrastructure`. Those are your two single-points-of-failure. Everything else self-heals; these two don't.

```bash
# ─────────────────────────────────────────────────────────────
# C. THE SMOKING GUN — prove the root does NOT own infrastructure
# ─────────────────────────────────────────────────────────────
kubectl get kustomization flux-system -n flux-system \
  -o jsonpath='{range .status.inventory.entries[*]}{.id}{"\n"}{end}' \
  | grep -i infrastructure \
  && echo ">>> root OWNS infrastructure (would self-heal)" \
  || echo ">>> root does NOT own infrastructure — it is an unowned APEX (will not self-heal)"
```

```bash
# ─────────────────────────────────────────────────────────────
# D. PROVE infrastructure owns the 32 children — count them
# ─────────────────────────────────────────────────────────────
kubectl get kustomization infrastructure -n flux-system \
  -o jsonpath='{range .status.inventory.entries[*]}{.id}{"\n"}{end}' \
  | grep -ci 'Kustomization'
# → expect ~32. That's the blast radius of one delete.
```

```bash
# ─────────────────────────────────────────────────────────────
# E. THE PATHS SIDE BY SIDE — why infrastructure is unowned
#    (its path is OUTSIDE the folder the root renders)
# ─────────────────────────────────────────────────────────────
echo "root renders:           $(kubectl get kustomization flux-system   -n flux-system -o jsonpath='{.spec.path}')"
echo "infrastructure renders: $(kubectl get kustomization infrastructure -n flux-system -o jsonpath='{.spec.path}')"
```
**What you'll see:** the root renders `clusters/fanatics-exchange/dev-1`. If `infrastructure`'s manifest does **not** live inside that folder, the root never applies it → it's the orphan-apex. That single fact is the root cause of "didn't come back."

---

**The story these five tell, in order:**
- **A** = the whole ownership tree at a glance (who heals whom).
- **B** = the exact list of objects that *can't* heal — your danger list.
- **C** = proves `infrastructure` isn't under the root.
- **D** = proves deleting it takes 32 things down.
- **E** = explains *why* it's unowned (its manifest lives outside the root's path).

Paste back **A** and **E** especially — those two together show the entire flaw on one screen.
